### Архитектурное решение

`iikoServer → background sync → EOS DB → analytics API → UI`

Продажи загружаются из iiko только в фоне. EOS DB хранит факты и snapshots;
EOS рассчитывает метрики и контролирует доступ. Analytics API, UI, Reports и
экспорты используют данные EOS DB без синхронных обращений к iiko.
Неполные периоды явно обозначаются, сравнение остаётся предварительным;
финальный snapshot не создаётся до полноты выбранного и предыдущего периодов.
При ошибке обновления сохраняются последние успешные данные.

# 1. Цель

Раздел **«Статистика»** предназначен не просто для отображения продаж, а для количественной оценки работы розничной сети и продавцов.

Основные задачи:

- продавец понимает собственный результат и выполнение KPI;
- управляющий Эклеров видит состояние всей розничной сети;
- операционный директор контролирует план/факт, KPI сети и сотрудников, требующих внимания;
- директор получает полный доступ к аналитике;
- шеф-кондитер и заведующий производством получают статистику продаж выпускаемой продукции;
- руководители могут проваливаться из агрегированного показателя до причины: **сеть → точка → продавец / продукция**.

Отдельный сводный «KPI-балл» сотрудника в первой версии **не создаётся**.

# 4. Основные метрики продавца

Продавцу нужны ровно четыре основных показателя.

| Метрика | Назначение |
|---|---|
| Средний чек | KPI |
| Наполняемость | KPI |
| Личная сумма продаж | Информационная |
| Количество чеков | Информационная |

## 4.1 Средний чек

Рассчитывается по сумме **после скидок**:

`Средний чек = фактическая сумма продаж / количество учтённых чеков`

Цель устанавливается на уровне всей розничной сети.

## 4.2 Наполняемость

Наполняемость — среднее фактическое количество **единиц товара** в чеке.

Пример:

`2 эклера + 1 кофе = 3 единицы`

Формула:

`Наполняемость = сумма проданного количества / количество учтённых чеков`

Две одинаковые единицы товара считаются двумя единицами, даже если находятся одной строкой чека.

**Бесплатные позиции исключаются из расчёта наполняемости.**

Историческое условие discovery: точное OLAP-поле количества требовалось подтвердить через:

`GET /resto/api/v2/reports/olap/columns?key=<token>&reportType=SALES`

## 4.3 Личная сумма продаж

Сумма товаров, фактически проданных сотрудником за выбранный период после скидок.

Цели по этому показателю **нет**.

## 4.4 Количество чеков

Количество учтённых чеков продавца.

Цели по показателю **нет**.

# 5. Возвраты и исключения

Полностью возвращённый чек **не участвует в статистике**:

- не входит в выручку;
- не входит в количество чеков;
- его товары не входят в наполняемость;
- его товары не входят в продажи продукции.

OLAP-запросы должны учитывать удалённые заказы и позиции через поля:

- `DeletedWithWriteoff`
- `OrderDeleted`

Документация показывает применение `NOT_DELETED` как рабочего значения для исключения удалённых сущностей.

Механика **частичного возврата** должна быть подтверждена на фактических данных iiko во время технической разведки. Не фиксировать по предположению.

# 6. Цели

В первой версии существуют три плановых показателя.

## KPI розницы

- целевой средний чек;
- целевая наполняемость.

Цели пока устанавливаются **одинаково для всей сети**.

## Бизнес-план

- план месячной выручки сети.

Это не KPI отдельного продавца, а отдельный плановый показатель бизнеса.

---

# 7. История целей

Цель не перезаписывается.

Хранится история:

`показатель + период действия + значение + кто установил + дата изменения`

Пример:

| Период | Средний чек | Наполняемость | План выручки |
|---|---:|---:|---:|
| Октябрь 2026 | 700 ₽ | 3,00 | 6 000 000 ₽ |
| Ноябрь 2026 | 730 ₽ | 3,10 | 6 300 000 ₽ |

Редактировать цели может **только `DEPUTY_DIRECTOR`**.

`DIRECTOR` имеет просмотр, но не изменение.

Изменение цели обязательно логируется через audit trail.

---

# 8. Цветовая оценка KPI

Для среднего чека и наполняемости рассчитывается:

`выполнение = факт / цель × 100%`

Состояния:

- цель выполнена или превышена — зелёное;
- отставание менее 15% — предупреждающее/нейтральное;
- выполнение ниже 85% цели — красное.

Красный цвет **не используется для небольшого недовыполнения**.

Базис — предыдущий период такой же продолжительности.

Примеры:

- `1–10 октября → 21–30 сентября`
- `текущая неделя → предыдущая неделя`
- `текущий месяц → предыдущий месяц`

Для KPI основной показатель на экране — **факт относительно установленной цели**.

# 23. Источник — iikoServer OLAP v2

Документация по iikoServer указывает два способа работы:

1. использовать сохранённый в iikoOffice OLAP-отчёт;
2. формировать OLAP-запрос самостоятельно.

Для EOS выбирается программно формируемый запрос.

Документация рекомендует **OLAP v2**.

## Каталог полей

Обязательный discovery-запрос:

```http
GET /resto/api/v2/reports/olap/columns?key=<token>&reportType=SALES
```

Ответ содержит для каждого `FieldName`:

- `name`
- `type`
- `aggregationAllowed`
- `groupingAllowed`
- `filteringAllowed`
- `tags`

Поддерживаемые типы включают:

- `ENUM`
- `STRING`
- `ID`
- `DATETIME`
- `INTEGER`
- `PERCENT`
- `DURATION_IN_SECONDS`
- `AMOUNT`
- `MONEY`

---

# 24. Формирование OLAP-запроса

Основной endpoint:

```http
POST /resto/api/v2/reports/olap?key=<token>
Content-Type: application/json
```

Документированная структура:

```json
{
  "reportType": "SALES",
  "buildSummary": true,
  "groupByRowFields": [],
  "groupByColFields": [],
  "aggregateFields": [],
  "filters": {}
}
```

`groupByRowFields`, `groupByColFields`, `aggregateFields` и `filters` должны использовать фактические `FieldName`, разрешённые схемой `/columns`.

## buildSummary

Значение задавать явно.

Документация указывает:

- до iiko 9.1.2 default = `true`;
- начиная с iiko 9.1.2 default = `false`.

EOS не должен зависеть от server default.

| `DeletedWithWriteoff` | состояние удаления позиции |
| `OrderDeleted` | состояние удаления заказа |

Пример отчёта «Выручка по дням» использует:

- `OpenDate`
- `GuestNum`
- `DishSumInt`
- `DishDiscountSumInt`
- `UniqOrderId`

Пример «Выручка по официантам» использует:

- `WaiterName`
- `DishSumInt`
- `DishDiscountSumInt`

Пример «Выручка по категориям блюд» использует:

- `DishCategory`
- `GuestNum`
- `DishSumInt`
- `DishDiscountSumInt`
- `UniqOrderId`

# 26. Фильтрация удалённых сущностей

Подтверждённые примеры фильтров:

```json
{
  "DeletedWithWriteoff": {
    "filterType": "IncludeValues",
    "values": ["NOT_DELETED"]
  },
  "OrderDeleted": {
    "filterType": "IncludeValues",
    "values": ["NOT_DELETED"]
  }
}
```

В документации также показан вариант:

```json
{
  "DeletedWithWriteoff": {
    "filterType": "ExcludeValues",
    "values": [
      "DELETED_WITH_WRITEOFF",
      "DELETED_WITHOUT_WRITEOFF"
    ]
  }
}
```

Точный вариант для production должен быть выбран после сверки с фактическим iikoOffice-отчётом.

# 27. Фильтр периода OLAP

Подтверждённый формат:

```json
{
  "OpenDate": {
    "filterType": "DateRange",
    "periodType": "CUSTOM",
    "from": "2026-10-01T00:00:00.000",
    "to": "2026-11-01T00:00:00.000"
  }
}
```

Документация также поддерживает periodType:

- `CUSTOM`
- `OPEN_PERIOD`
- `TODAY`
- `YESTERDAY`
- `CURRENT_WEEK`
- `CURRENT_MONTH`
- `CURRENT_YEAR`
- `LAST_WEEK`
- `LAST_MONTH`
- `LAST_YEAR`

В ingestion рекомендуется использовать `CUSTOM`, чтобы EOS сам контролировал границы периода.

# 28. Исторические ограничения до discovery

До discovery на живом iikoServer не фиксировать точные `FieldName` для:

- количества проданного товара;
- стабильного ID товара;
- стабильного ID сотрудника;
- сотрудника кассы;
- подразделения/торговой точки;
- стабильного ID точки;
- конкретного чека/заказа;
- бесплатности позиции;
- частичного возврата;
- итоговой суммы в точном смысле используемого пользователем OLAP-отчёта.

Эти поля должны быть выбраны только после анализа:

`/resto/api/v2/reports/olap/columns?reportType=SALES`

# 29. Привязка сотрудников

CURRENT: seller attribution использует confirmed stable iiko identity и
подтверждённую связь iiko employee → Employee → User. Доступ SELLER определяется
аутентифицированным User, а не переданным клиентом employee ID.

Исторический эскиз до discovery:

`iiko employee ID → Employee.iiko_user_id → User`

Доступ `SELLER` строится по этой связи.

Если OLAP возвращает только имя, использование ФИО как основной связи **запрещено**, пока не доказано отсутствие ID-поля.

ФИО допустимо только как диагностический fallback при первоначальной сверке.

# 30. Привязка точек

Нужно найти в `/columns` стабильный идентификатор подразделения/группы, соответствующий торговой точке.

`CashRegisterName` допустимо использовать для диагностики, но не как основной ID точки, если iiko предоставляет стабильный идентификатор подразделения.

После нахождения ID:

`iiko retail unit → Department`

В статистический scope допускаются только розничные точки EOS.

# 31. Архитектура хранения

UI **не обращается напрямую к iiko**.

Схема:

`iikoServer → background sync → EOS DB → analytics API → UI`

Причины:

- снижение нагрузки на iiko;
- отсутствие задержек при открытии страницы;
- контроль прав в EOS;
- история;
- snapshots;
- KPI;
- повторное использование данных;
- работа при временной недоступности iiko.

---

# 32. Исторический эскиз минимального внутреннего факта продажи

Окончательная схема утверждается после `/columns`, но хранилище должно позволять восстановить как минимум:

```text
closed_at

iiko_order_id

employee_id

```

EOS хранит **первичный факт**, а не только агрегированные показатели.

# 33. Контрольные запросы

До реализации пользовательского UI выполняется обязательная верификация.

## 33.1 Контроль №1 — точка

Период:

**1 день + 1 розничная точка**

Сверить EOS с iikoOffice по:

- выручке после скидок;
- количеству чеков;
- среднему чеку;
- количеству проданных единиц;
- наполняемости.

Ожидаемое расхождение:

**0**, кроме заранее объяснённого округления.

## 33.2 Контроль №2 — продавец

Период:

**1 продавец + 1 день**

Сверить:

- сумму продаж;
- чеки;
- средний чек;
- количество товара;
- наполняемость.

## 33.3 Контроль №3 — продукция

Период:

**1 позиция + несколько розничных точек**

Сверить:

- количество;
- выручку;
- точки;
- период.

После трёх успешных сверок OLAP-контракт считается подтверждённым.

---

# 34. Нагрузка

Синхронизация выполняется каждые 15 минут.

Не делать один огромный OLAP-запрос со всеми возможными измерениями, если он создаёт чрезмерную кардинальность и нагрузку.

Разрешается разбивать ingestion на несколько специализированных запросов после замеров на живом iikoServer.

OLAP-запросы по остаткам в Stage 3.1V-A **не используются**.

# 38. Зафиксированные продуктовые решения

Ниже сохранены исходные продуктовые решения, принятые перед A0:

- раздел называется **«Статистика»**;
- продавец видит только себя;
- продавец не видит деньги точки и сети;
- KPI продавца: средний чек + наполняемость;
- сумма продаж и чеки — информационные показатели;
- наполняемость считается в физических единицах товара;
- бесплатные позиции исключаются;
- средний чек считается после скидок;
- полностью возвращённый чек исключается;
- цели пока единые для всей розничной сети;
- цели задаются на месяц;
- менять цели может только `DEPUTY_DIRECTOR`;
- красное состояние — ниже 85% цели;
- основная пользовательская аналитика — неделя и месяц;
- history UI — 6 месяцев;
- storage — бессрочно;
- sync — каждые 15 минут;
- weekly report — внутри EOS по понедельникам;
- snapshots обязательны;
- экспорт Excel/PDF обязателен;
- уволенные скрыты из активной выборки, но доступны по фильтру;
- Dashboard-виджеты утверждены:
  - SELLER `1×1`;
  - NETWORK_MANAGER `1×2`;
  - DEPUTY_DIRECTOR `1×2`;
  - DIRECTOR аналогичный `1×2`.
