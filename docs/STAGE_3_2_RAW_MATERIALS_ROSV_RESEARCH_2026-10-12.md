# Stage 3.2 — разведка РОСВ для «Сырья», 12.10.2026

Статус: **RESEARCH / REVIEW; разработка не начата**.

## Подтверждённый результат

С текущими правами интеграции доступны остатки склада на дату, подробные движения и экспорт приходных/расходных накладных. Из них воспроизведены количественный и денежный балансы сентября по **164 UUID**: все остаточные расхождения равны нулю в точности возвращённых API значений. **99 пар «UUID приходного документа + UUID товара»** из 38 проведённых приходов совпали с движениями по количеству и сумме.

Это подтверждает составной путь получения показателей РОСВ, но **не идентичность конкретной форме iikoOffice**: контрольный экспорт РОСВ владельца не предоставлен. Отдельный endpoint точной расширенной формы не подтверждён. OLAP по проводкам реально запрещён текущими правами: HTTP 409, `B_VOTR` («Просматривать OLAP-отчет по проводкам»). Права не изменялись.

Закупочные цены извлекаются из проведённых приходов, а не из РОСВ. Для сахара, пшеничной муки и пудры рассчитаны сопоставимые документные средние; у сливок общая средняя за шесть месяцев **заблокирована из-за единиц PCS/KG**. У шести остальных контрольных позиций в исследованном интервале нет приходов: цена остаётся неизвестной. Проведённость документа сама по себе не подтверждает внешнюю закупку и качество первичного документа.

## Проверка полного сентябрьского баланса

Для каждого UUID отдельно проверены `остаток_начало + Σsigned_движений = остаток_конец` и аналогичное денежное равенство. Использован Decimal; максимальные остаточные расхождения количества и суммы **0E-9**. Отсутствие строки остатка принимается за ноль **только в проверочной арифметике**; исходное отсутствие остаётся NULL и не превращается в нулевую закупочную цену.

Наивная цифра 383.330677 из смешанных единиц сохранена только в JSON как диагностическая исходная арифметика; `comparable_document_average=NULL`, статус `MIXED_UNITS_BLOCKED`. Это не утверждённая цена.

**Сахар:** документ `5bf2b1c7-8c91-b774-01a0-ae4cafa53ba1`, №EOS-CONTRACT-20260917-001, 1 кг / 105.90 — ранее документированный технический contract smoke ([аудит Supply](STAGE_3_SUPPLY_AUDIT_2026-09-18.md)). Он исключён **аналитически по точному UUID** из закупочной средней: 155229.34 / 1799 кг = 86.286459144. В балансе и сверке движения сохранён, исходный документ не изменён. Нельзя исключать все номера `EOS-*`: такой же префикс есть у последнего прихода пудры и не доказывает его технический характер.

## Как отделить расход сырья от перемещений и корректировок

1. Зафиксировать склад UUID, календарный период и справочные единицы; получить все движения с документными UUID и знаками, отдельно сохранить корректировки.
2. Разделить приход, TRANSFER, инвентаризацию, корректировку стоимости, SESSION_WRITEOFF и WRITEOFF. Последние два не объявлять производственным расходом без причины/исходного документа.
3. Для OUTGOING_INVOICE прочитать исходный документ. Если сырьевой UUID является прямой строкой накладной, это непосредственная передача/отпуск сырья; его нельзя автоматически назвать потреблением в ТТК. Если исходные строки — готовые изделия, а движение сырья сформировано их разложением, сохранить отдельный показатель **«Учётное списание ингредиента при передаче готовой продукции»**.
4. В проверенных десяти позициях все соответствующие расходные движения соединены с исходными документами, отсутствующих документов нет. Прямых строк этих сырьевых UUID в исходных накладных не найдено. Сахар, сливки, обе расходуемые муки, пудра и сэндвич-упаковка отражены как производные списания при передаче готовой продукции.
5. Не исключать весь OUTGOING_INVOICE как «перемещения»: это удалило бы основной доступный учётный расход сырья. Не смешивать его с физически измеренным выпуском/потерями, фактическим потреблением партии или плановой калькуляцией EOS. Доступная связь UUID документа не распределяет каждую долю сырья на конкретную строку готового изделия.

Возвраты проверены отдельно. При фильтре RETURNED_INVOICE с включёнными корректировками API вернул одну **STORE_COST_CORRECTION** от 28.05: количество 0, сумма −250.55, `incoming=true`. Это не возврат и не закупка. При `showCostCorrections=false` осталось 0 строк. Следовательно, одного `incoming` или запрошенного типа недостаточно: нужно проверять фактические `type`, `documentType`, знак и нулевое количество. Отсутствие этого типа в данном периоде не доказывает отсутствие иных способов отражения возврата.

## Детализация по поставщикам

Приходы можно группировать по `(product UUID, supplier UUID, amountUnit UUID)` с количеством, суммой и средней. В строках целевого склада за апрель–12 октября обнаружены 12 контрагентов, включая двух представителей магазинов и одного сотрудника. Справочник `/api/suppliers` позволяет сохранить `is_supplier`, `represents_store`, `is_employee`, `deleted`. Флаг `is_supplier` не отменяет остальные признаки.

В evidence есть 15 групп по десяти контрольным позициям. **supplier_prices — сырая диагностическая группировка, не принятая закупочная цена**: единицы разделены, но технический сахарный приход присутствует в соответствующей группе. Для принятой средней использовать отбор purchase_lines с `technical_smoke=false` и проверкой единицы/контрагента. Имена сотрудников исключены из evidence; UUID и признаки сохранены.

Достоверно разложить **конечный остаток или расход** по поставщикам нельзя: баланс и движения не дают подтверждённой партионной связи, OLAP проводок запрещён. Распределять остаток пропорционально закупкам или назначать последнего поставщика всему остатку недопустимо.

## Что можно использовать после review, и что остаётся открытым

Для будущей базы знаний подтверждён доступ к UUID сырья, текущей справочной единице, остаткам/оборотам выбранного склада, документным закупочным строкам и поставщикам приходов. Хранить следует происхождение, дату/период, единицу, налоговую базу и статус качества каждого показателя. **Учётная стоимость остатка**, **документная закупочная средняя** и **плановая себестоимость EOS** должны оставаться разными показателями. Это вывод исследования, а не выполненная реализация моделей/API/UI.

До принятия закупочной цены нужны решения/подтверждения: исторический коэффициент PCS→KG для сливок; трактовка контрагента-сотрудника и внутренних контрагентов; налоговая база и валюта; допустимый срок давности цены при отсутствии прихода. Нет оснований автоматически снимать блокировки или брать цену из другого склада.

Для независимого подтверждения РОСВ нужен экспорт iikoOffice за сентябрь именно этого склада с параметрами отчёта/единицами. Текущие права не позволяют проверить OLAP по проводкам; расширение прав в задачу не входит. Исследование не подтверждает точность физических остатков, первички поставщиков или фактического производственного потребления только внутренней сходимостью API.
