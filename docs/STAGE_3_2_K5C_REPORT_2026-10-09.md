## Семантика iiko и внешние источники

Текущие официальные страницы прочитаны 09.10.2026; определения —
[iikoOffice 9.2](https://ru.iiko.help/article/iikooffice-9-2/topic-3?cm=1&ds=1&gc=1),
остатки — [iikoServer reports v2](https://ru.iiko.help/article/api-documentations/otchety-vv2?cm=1&ds=1&gc=1).
Сборка удалённого iikoServer/Office в этом проходе не установлена.

| Показатель | Что означает и почему не взаимозаменяем |
|---|---|
| ССС | Скользящая средневзвешенная складская стоимость: денежный остаток / количество; при отсутствии приходов возможна ручная оценка. Нужен конкретный склад/момент |
| СПП | Последний приход, влияющий на запас; не только закупочная накладная, но и приготовление/переработка/перемещение |
| ССН | Нормы ТТК × стоимость ингредиентов по ССС. Оценочный ингредиент делает оценочным итог. Составной DIRECT ингредиент без приходов не обязательно раскрывается до сырья: может использовать оценку |
| ССНПП | Сырьевой набор с оценкой ингредиентов по последнему приходу; без приходов возможна оценочная стоимость. Настройки расчёта не менялись |
| ССН’ | Расчёт несохранённых изменений Office; не самостоятельная опубликованная версия ТТК |

Обычный показатель iiko «Себестоимость» выбирает ССС для товаров и готового
списания, ССН — для списания ингредиентов. На всех четырёх скринах режим
**«Списывать готовое блюдо»**. Поэтому колонка EOS должна иметь пояснение
«Сырьевой набор, ССН», иначе пользователь может ожидать ССС.

| Источник / метод | Проверка и применимость |
|---|---|
| `assemblyCharts/getTree`, `getPrepared` | Live GET четырёх existing UUID. Нормы/версия доступны, готового денежного показателя нет. SOURCE состав и PREPARED списание не смешиваются |
| `entities/products/list` | Bounded UUID roots/dependencies. В сохранённой cost-проекции нет вычисленной current cost; `estimatedPurchasePrice=0` не используется как fallback |
| `reports/balance/stores` | Live количественный `amount` и денежный `sum` по product/store/timestamp. Это источник оценки остатков, не готовая ССН и не СПП. При quantity=0 или неизвестном входе деление запрещено |
| OLAP TRANSACTIONS columns | Live metadata, HTTP 200. Есть `FinalBalance.Money`, `FinalBalance.Amount`, `Product.AvgSum`, `Amount.In`, `Sum.Incoming`, `Sum.Outgoing`. Денежный отчёт не ограничивается SALES. Числовой TRANSACTIONS report здесь не строился; средняя цена операций не объявляется current cost или last receipt |
| OLAP SALES | K5A подтвердил historical `ProductCostBase.ProductCost/OneItem`. Повторный SALES report не требовался. Продажи не источник текущей ТТК; нет продажи — нет cost row |
| Приходные накладные / складские документы | Existing EOS readers изучены. Цена одной накладной не воспроизводит ССС/СПП с учётом всех приготовлений, перемещений, корректировок. Полный журнал и независимая точность такого воспроизведения не подтверждены; в этом проходе документы не загружались |
| iikoOffice экран/экспорт | Четыре независимых скрина владельца — контроль расчёта. Подходят для verified manual observation с отдельным provenance, но ручная выгрузка не решает автоматическое обновление |
| Закрытый Office RPC / альтернативный endpoint | Недокументированные методы расчёта не угадывались и не вызывались. Требуется подтверждённый контракт поставщика, если нужен именно расчёт самого iiko |

Existing `map_stock_balance`/`IikoStockBalanceDto` сохраняют количество, но
**не проецируют `sum` в DTO**. Будущая денежная интеграция должна читать отдельный
строгий money contract; нельзя менять действующие расчёты Supply или принимать
его quantity DTO за денежный snapshot. Existing client даёт auth/TLS/последовательные
запросы/logout. K3 `price_refresh` и K5B `recipes` дают seams immutable
observation/publication и Automation Core; повторного scheduler не требуется.

### Что мешает считать кандидат подтверждённым источником

1. Эмпирический all-store positive pool воспроизводит две суммы, но это
   **не подтверждённый алгоритм iiko для production склада**. На all-store signed
   pool результаты 365,48 / 146,32 / 24,25 / 17,69; на candidate production store
   signed pool — 368,08 / 152,38 / 24,20 / 17,72. Ни один такой вариант не
   подменяет значения Office.
2. EOS mapping `key:a83edb2217d10e87` имеет source name «Цех Производство ИП»,
   status CONFIRMED, role MAIN, EOS department «Цех производство». Это не
   доказательство, что он соответствует указанному владельцем Office контексту.
   `/api/corporation/groups` и `/departments` вернули HTTP 200, но 6/10 скрытых
   records и ни одного видимого целевого цеха. Existing group reader fail-closed
   отклонил такой список. Не применять name-based mapping.
3. Ванилин: остаток `-0.31469342`, сумма `-101.17`; положительных остатков в
   полученной выборке нет. Ручная оценка API равна 0, её достоверность не установлена.
   Нельзя заменить вход нулём или считать signed ratio подтверждённой ССС.
   Промежуточная оценка 15,39 с пропущенным входом отброшена; строгий результат NULL.
4. Office стоимость единицы сахара у Малины 91,59, у Плюшки 91,97 при одном
   артикуле 00178. API all-store ratio 91,589429587. Это самостоятельное
   свидетельство разного/cached контекста; причина не доказана. Для теста
   воспроизводимости нужны повторные обновлённые снимки в одинаковом контексте.
5. У Сосиски и теста Медовика есть расхождение порядка копейки на исходных
   единичных стоимостях. Денежные суммы balance округлены до копеек, а quantity
   имеют больше знаков; точность/кэш/момент расчёта — гипотезы, не установленная
   причина. Нельзя искусственно подгонять округление по одному изделию.
6. Root API strategy ASSEMBLE и наличие PREPARED не отменяют Office готового
   списания. Effective DIRECT/store restrictions и политика вложенных узлов
   требуют отдельной проверки. Net/output/loss percentages не умножаются повторно
   на gross норму; масса изделия не заменяет базовую единицу «шт».

## Рабочий прототип и воспроизведение

- [`k5c_probe.py`](../scripts/k5c_probe.py): operator-only read-only сбор четырёх
  existing UUID, source guard, bounded product filters; DB READ ONLY + rollback,
  sequential API, TLS, timeout 30s/retries=0, logout. Нет enqueue/import/write.
  All-store stock запрос нужен для проверки гипотезы, не для автоматического
  выбора склада. stdout — zlib/base64 evidence с UUID hashes.
- [`k5c_cost_prototype.py`](../scripts/k5c_cost_prototype.py): автономный Decimal
  расчёт по SOURCE `amountIn/assembledAmount`, рекурсивно для ASSEMBLE;
  DIRECT nested — складская оценка. COMMON без specific department/size scope;
  остальные случаи fail closed. Число выдаётся только в `diagnostic_amount`;
  `amount=NULL`, `publication_allowed=false` **всегда**.
- [`evidence`](evidence/STAGE_3_2_K5C_2026-10-09.json): полный сохранённый проход
  четырёх изделий, Office transcription, входы и три экспериментальные политики.
  Hash UUID — псевдоним, не ID для API и не новый mapping. Нет credentials,
  source URLs, технологий или персональных данных сотрудников.

## План реализации после подтверждения денежного контракта

Это **предложение для review**, не внедрение и не разрешение включить расписание.

1. Зафиксировать точные UUID склада/подразделения Office; обновить одинаковым
   способом четыре контрольные карточки и их стоимости ингредиентов. Получить
   подтверждение ванилина, оценочности, tax/currency basis и источника текущей
   цены при нулевом/отрицательном запасе. Если нужен direct iiko calculated cost,
   запросить документированный поддерживаемый контракт у iiko/интегратора.
2. Выбрать один подтверждённый метод. Direct ответ хранить как `IIKO_SSN`;
   расчёт EOS — отдельно `EOS_RECIPE_ESTIMATE`, даже при равенстве Office.
   Нельзя переключать эти методы незаметным fallback. Historical sold cost
   никогда не публиковать в current pointer. Если точного источника нет —
   `MISSING_SOURCE` / amount NULL; Q05 остаётся открыт, Q15 требует решения владельца.
3. Отдельные immutable cost observations, без price/recipe mutations:
   tenant/source/product UUID, method/source, amount nullable, currency,

   estimated flag, quality/issues и independent verification provenance.
   Историю сохранять; новый current pointer только для полностью проверенного
   того же scope. Новая recipe/dependency версия инвалидирует старую актуальность.
   Любое schema изменение — новая Alembic migration с отдельной проверкой.
4. Existing Automation Core action `products.sync_iiko_costs`: execution →
   transactional outbox → existing worker/local action → existing iiko client →
   атомарная observation/publication. Source lock/идемпотентность и terminal

   его устаревшим; retry/timeout — existing execution flow. Вычисления в EOS,
   n8n не нужен; при выборе n8n он только читает API и возвращает versioned

5. Начать с четырёх UUID, одного подтверждённого scope и ручного обновления;
   проверить repeat/no-change, missing/negative/estimated/correction, смену
   версии и повтор callback. После приёмки — existing Regulatory Tasks schedule,
   например ежедневно после согласованной точки складского учёта; время/частоту
   подтвердить с бухгалтерией. Расписание сейчас не создаётся. В request path
   каталога/card нет обращения к iiko, только EOS DB.

## Отображение в портале

В существующей таблице «Продукция» колонка **«Себестоимость»** с пояснением
**«Сырьевой набор, ССН»**: сумма и единица `₽/шт` только при подтверждённом
currency/unit contract. Явный единый контекст склада для таблицы; разные склады
не смешивать в одну сумму. Missing — «Нет данных»; unverified — «Требует проверки»;
stale — предыдущее число с отметкой времени и «Устарело». Source zero отличать
от отсутствия данных. EOS estimate подписывать «Расчёт EOS», оценочный вход —
«Оценочная», без выдачи за «Рассчитано iiko».

В существующей карточке отдельный блок: показатель, метод, источник, склад,
подразделение, единица/база расчёта, действующая версия/дата ТТК,
дата stock snapshot и время получения/расчёта, качество и причины missing/stale.
ССС готового изделия показывать отдельно только при собственном подтверждённом
контракте. Экран не должен раскрывать raw payloads или execution IDs.

Денежные поля требуют **отдельного backend cost-read capability** и решения о
ролях; recipe/public product read не предоставляют автоматически доступ к деньгам.
Запрет должен работать в API таблицы, карточки и экспортов, а не только в JSX.
Frontend использует существующие components, loading/disabled/duplicate guards.
UI код и grants в этом исследовании не менялись.

видимых изделий**, включая единственную строку со звёздочкой: артикул 76410.
Группы номенклатуры не считаются изделиями. Артикулы сохранены строками,
включая ведущие нули. [Транскрипция](evidence/STAGE_3_2_K5C_OFFICE_LIST_2026-10-09.json),
[исходные API-факты](evidence/STAGE_3_2_K5C_MASS_2026-10-09.json),
[построчная сверка](evidence/STAGE_3_2_K5C_RECONCILIATION_2026-10-09.json).

43 артикула разрешены в UUID через опубликованные source-first записи EOS,
затем проверены по **артикулу и коду** в bounded API product response.
Шесть (11612, 76070, 12441, 76411, 76069, 11602) отсутствуют в опубликованном
EOS-каталоге: UUID получены из iiko по уникальной паре артикул/код. Они **не
добавлялись** в EOS. Названия используются только для подписи; автоматического
mapping по имени нет. В evidence UUID представлены стабильными SHA256 keys,
операторские API-запросы используют настоящие UUID. Продукты/склады не объединяются.

Основной денежный снимок 43 изделий: 16:16:35 +05:00; оставшиеся шесть
получены отдельным bounded проходом, timestamp записан в evidence.
Ограничения списания и единицы перепроверены дополнительным read-only проходом.
Это серия API чтений, а не единая транзакция iiko; исторические скрины не объявлены
универсальной гарантией текущего значения в любой момент. Production HEAD
при разведке 4e4ff2fb7d29de1f4886bf49f5d6f4c5a3ac7ad4, Alembic 0078.

### Воспроизведённый алгоритм и границы доказательств

1. Выбрать действующую исходную ТТК UUID изделия на дату, интервал [from,to).
   Корень всегда оценивается по сырьевому набору, даже при списании готового блюда.
2. Для строки взять `amountIn` **в основной единице ингредиента** и разделить
   на `assembledAmount`. Масса `unitWeight` не заменяет шт/л/кг и не является
   дополнительным множителем. Вложенные полуфабрикаты раскрываются по собственному выходу.
3. Вложенный direct-writeoff продукт оценивается по складу, а не автоматически
   раскрывается до сырья. Решение зависит от `effectiveDirectWriteoffStoreSpecification`;
   одно поле `productWriteoffStrategy=ASSEMBLE` этого не устанавливает.
4. В эмпирическом Office aggregate: если есть положительные остатки — стоимость
   за единицу = Σ денежных сумм положительных остатков / Σ их количества.
   Если их нет, но есть отрицательные — отдельно помеченный **NEGATIVE_STOCK_RATIO**
   = Σ денежных сумм отрицательных остатков / Σ их количества. Отрицательные
   остатки не отбрасываются незаметно и не объединяются с положительными.
5. **Стоимость терминального ингредиента округляется до 0,01 ₽, ROUND_HALF_UP,
   до умножения на норму.** Вложенный вычисленный ССН не округляется на каждом
   уровне; итог изделия округляется до 0,01 ₽. Decimal, без float.
6. Пустой денежный вход, нулевой знаменатель, неоднозначная ТТК, цикл,
   неизвестный размер/подразделение/единица → **NULL**. Оценочная цена = 0
   из product DTO сама по себе не подтверждает намеренную оценку и не служит fallback.

Эти единые правила дают 49/49 числовых совпадений **только при диагностическом
выборе веток для двух неизвестных подразделений**. Строгая функция не разрешает
такой выбор и даёт **47/49 совпадений + 2 NULL**. Не создана таблица вручную
подогнанных цен по изделиям. Ни одна сумма из evidence не публикуется.

Официальные определения подтверждают SSN как сумму ингредиентов по ССС,
деление на норму закладки, различие ССС/СПП и распространение оценочности:
[определения iikoOffice 9.2](https://ru.iiko.help/article/iikooffice-9-2/topic-3?cm=1&ds=1&gc=1),
[пример iikoOffice 9.2](https://ru.iiko.help/article/iikooffice-9-2/topic-222?cm=1&ds=1&gc=1).
Точное правило pool положительных/отрицательных складов и порядок округления
**воспроизведены экспериментально по этой выборке**, не объявлены публичным
официальным API контрактом. Совпадение Office aggregate не доказывает, что
значение рассчитано только по производственному складу: candidate
`Цех Производство ИП` (key a83edb2217d10e87) отдельно даёт другие суммы.
Автоматическое сопоставление этому складу не выполняется.

### Почему прежний прототип расходился или возвращал NULL

- Прежнее деление stock sum/quantity без округления unit cost оставляло копеечные
  расхождения. Например 75683: 21,954034… → 21,95 против Office 21,96;
  новая unit-rounding версия → 21,955385… → **21,96**.
  75913: прежние 50,735445… → 50,74 против **50,73**; после unit rounding
  50,733355… → **50,73**. Аналогично 75800, 75808 и 75802.
- 19 из 49 прежних результатов NULL вызваны отсутствием положительного
  остатка требуемых ингредиентов, а не отсутствием ТТК. Например 00898
  «Мандарины», 00899 «Киви», 01162 «Ванилин» имеют отрицательные остатки.
  Полный signed pool всех складов также не воспроизводил Office. Разделение
  положительного pool и отрицательного-only ratio устраняет числовую причину,
  но остаётся эмпирическим методом, который требует явной Office сверки.
- X3 76243/76242: прежнее раскрытие готовых эклеров давало 83,51/71,16 ₽.
  Office оценивает вложенный готовый эклер по складской стоимости.
  Карамельный: round(989,08/8)=123,64; 3 × 123,64 + 17,65 = **388,57**.
  Сливочный: round(3397,35/25)=135,89; 3 × 135,89 + 17,65 = **425,32**.
  Эти вложенные ТТК имеют исключение по подразделению key fdd2b1a65bf40d86;
  для этого исключения должно применяться раскрытие, дающее другой результат.
  Точное подразделение Office не установлено по UUID, поэтому strict остаётся NULL.
- 00236 «корзинка фруктовая» и 75800 «Торт Праздничный»: source
  `productSizeAssemblyStrategy=SPECIFIC` первоначально блокировал расчёт.
  Дополнительный GET `entities/products/productScales` по реальным UUID в
  16:55:54+05:00 вернул явный `null` для обоих продуктов: шкалы размеров нет,
  а ни одна строка ТТК не имеет фильтра размера. Это не неизвестный выбранный
  размер, а неактивный режим. После проверки отсутствия шкалы strict даёт
  **33,32/313,16 ₽**. Наличие шкалы, отсутствие ключа в ответе или фильтр размера
  по-прежнему блокируют расчёт; collector дважды проверяет шкалы на изменения.
  [Документированный endpoint и пример явного null](https://ru.iiko.help/article/api-documentations/rabota-so-shkaloy-i-razmerami).
  Факты дополнительного прохода сохранены в `size_scope_check` массового evidence.
  Временный probe завершился ошибкой при вызове `close` вместо `aclose` после
  выдачи результатов; HTTP 200 и значения null были получены до ошибки.
  Это не ошибка endpoint или расчёта. Постоянный collector использует штатный async context manager.
- При повторной проверке полного справочника одна пара артикул/код не дала
  уникальную строку; bounded запрос по уже установленному EOS UUID её подтвердил.
  Не использована замена по похожему названию.

### Звёздочка, нули и оценочные цены

На карточках Office указана легенда: приблизительные значения при отсутствии
приходов. Документация связывает оценочность ССН с хотя бы одним оценочным
ингредиентом. На списке звёздочка есть у **76410 / 113,08 ₽**.
У его контейнера 76407: остаток **−27 шт, сумма 0**, `estimatedPurchasePrice=0`.
Такое значение воспроизводит денежный итог, но **не доказывает отсутствие
приходов**. Нельзя вывести оценочный статус только из знака остатка или цены = 0.

Новая реализация не подставляет денежный ноль при missing input. Истинный
source sum=0 может участвовать в диагностике, с ZERO_VALUATION_REQUIRES_REVIEW.
Публичные деньги и звёздочка разрешаются только после независимого Office
подтверждения. Оценочное подтверждение/zero valuation не наследуется следующим
автоматическим снимком: без доказательства актуального статуса нужны повторная
Office сверка или отдельный источник истории приходов/официального cost flag.
Исторический SALES cost не используется как замена.

## Локальная реализация и автоматическое обновление

- `app/product_knowledge/cost_calculation.py`: независимая Decimal функция с
  разложением до терминальных ингредиентов, norm/basis/path, units, rounded unit
  cost, contribution, рисками и сигнатурой метода. В UI показан развёрнутый
  сырьевой набор; direct-writeoff полуфабрикат/готовое изделие остаётся терминалом.
- `app/product_knowledge/costs.py`: UUID-only bounded collection, отдельный
  monetary reader сохраняет `sum` и не меняет mapper/DTO Supply. Фиксированный
  source-local timestamp, batch ≤50 UUID, общий reference limit 2000,
  tenant/source/product/unit guards, повторное чтение дерева против изменения
  ТТК во время сбора. Сбор вне DB-транзакции, сохранение внутри outbox finalization.
- `app/models/product_cost.py`, Alembic **20261009_0079**: append-only
  `product_cost_observations` и `product_cost_verifications`; source/product
  tenant FKs, execution/product uniqueness, PostgreSQL запрет UPDATE/DELETE,
  запрет downgrade при наличии истории. Нет bootstrap денег, прав в production
  или автоматически созданных расписаний.
- Существующее action `products.sync_iiko_costs` в local action executor:
  Execution → Outbox → iiko reads → lease/terminal guard → observation + audit +
  SUCCEEDED одной транзакцией. Повтор execution с другим содержимым отвергается.
  n8n и новая параллельная очередь не вводятся.
- Существующий scheduler/регламент: **interval 60 минут**, company scope,
  явные UUID продукции и складской context. Настройка регламента требует
  Office verification с `allow_updates=true` для каждого включённого UUID.
  Первые наблюдения всегда UNVERIFIED/INCOMPLETE, без публичных денег.
- Protected cost projection показывает только exact independently confirmed
  snapshot. `allow_updates=true` разрешает автоматический сбор новых наблюдений,
  **не перенос Office подтверждения на новую сумму**. Проверенный метод и тот же
  набор складов не доказывают оценочность нового снимка: доступный API не выдаёт
  звёздочку Office/надёжный статус приходов. Поэтому новые наблюдения всегда
  скрыты до сверки; автоматическая публикация текущих сумм остаётся блокированной.
  Changed recipe, stock method, zero/estimated state также требуют новой сверки.
  Новое INCOMPLETE не подменяется предыдущей хорошей суммой. Неоднозначные
  contexts требуют явного выбора.
  Current snapshot старше двух часов или из будущего скрыт; история отдельно
  подписана как историческая. Чтение истории SQL-пагинировано, latest — window query.

**Права для review:** PRODUCT_COST_READ — ADMIN, HEAD_OF_PRODUCTION,
CHEF_CONFECTIONER, с существующими требованиями active employee/production context.
Это отдельная capability, доступ к каталогу/ценам не даёт доступ к деньгам.
PRODUCT_COST_REVIEW/CONFIRM — ADMIN, HEAD_OF_PRODUCTION, CHEF_CONFECTIONER
после финализации ограниченного выпуска; действуют существующие context/write guards.
Техническая загрузка — TECHNICAL_ADMIN.
Расширение на директора/бухгалтера здесь не выполнено автоматически.

API (request path без iiko):

- GET `/products`, `/products/{id}`: `cost_access`, защищённая проекция `cost`.
- GET `/products/{id}/costs`: contexts, current, пагинированная история, ingredient
  quantities/main units/unit costs/contributions, source/method/warehouse/timestamps.
- POST `/products/costs/refresh`: технический bounded enqueue, 202 означает
  постановку в очередь, а не готовность или успешную себестоимость.
- POST `/products/{id}/costs/confirm`: exact snapshot/content hash, independent
  Office SSN, estimated flag, явное подтверждение контекста, evidence;
  `allow_updates` по умолчанию **false**. Расхождение или stale/latest conflict → 409.

Frontend: существующая таблица получила условную колонку «Себестоимость»;
карточка — total SSN, source/method/context/warehouse/time, ingredient details,
history и безопасные loading/error states. Для unauthorized колонка/блок отсутствуют.
Для UNVERIFIED/INCOMPLETE/STALE API не возвращает деньги или денежные компоненты.
UI дополнительно проверяет status перед отображением суммы. Execution IDs,
raw input, stock rows и provider details не отображаются.
