## 1. Назначение и границы

Stage 3.2 состоит из двух строго последовательных частей:

1. **База знаний продукции** сети «Эклер»: ассортимент, карточки, подтверждённые
   сведения iiko и локальные дополнения EOS.
2. **Производственная потребность**: рекомендации, заявки, утверждение шефом,
   потребность в сырье и связь с Supply. Разработка начинается только после
   реализации и бизнес-проверки части I, включая gate K из дорожной карты.

База служит также фундаментом для аналитики себестоимости и обучения продавцов.
Самостоятельные тесты знаний, учебные курсы и новый BI-модуль этим этапом не обещаются.
Отдельный раздел с названием «Номенклатура» **не создаётся**.

Ограничение первоначального документационного прохода от 08.10.2026 допускало
только изучение локального кода и документацию. Задание K2 от 09.10.2026 отдельно
разрешило код, миграции, тесты и обновление документов; production deployment
остаётся неразрешённым. Текущий результат — в [отчёте K2](STAGE_3_2_K2_REPORT_2026-10-09.md).

## 4. Часть I — рабочий раздел «Продукция»

### 4.1 Таблица

**РЕШЕНИЕ:** семь основных колонок, в заданном порядке:

| Колонка | Отображение и неопределённости |
|---|---|
| Фото | Миниатюра кеша EOS, заглушка при отсутствии |
| Название | Название изделия; открытие карточки по ссылке |
| Вес | Число и единица с подтверждённой семантикой; неизвестное — «Нет данных» |
| Порционный / весовой товар | Подтверждённый тип продажи; единица сама по себе не доказывает тип |
| Цена | Действующая цена выбранной точки и даты, единица цены |
| Себестоимость | Только разрешённым ролям; сумма с контекстом метода/периода в карточке; неизвестное — «Источник не подтверждён» |
| Статус | Выпадающий список «В продаже» / «Выведено из продажи»; без права изменения — текст |

**ПРЕДЛОЖЕНИЕ:** над таблицей — поиск по названию/артикулу, фильтры статуса,
категории EOS, типа продажи, точка и дата цены. В основной таблице нет рецептур,
служебных идентификаторов или множества ценовых колонок. Если цены различаются,
нельзя выдавать случайную цену за сетевую: без выбора точки показать «Выберите
точку» либо подтверждённую одинаковую цену с явным сетевым контекстом (Q04).
Статус ассортимента в первой версии предлагается сетевым (Q01), цены — по точкам.

Поиск и пагинация выполняются backend. Состояния: загрузка, пустой каталог,
ничего не найдено, ошибка и устаревшие данные. Таблица читает EOS DB;
открытие страницы не запускает iiko-вызов. Поиск не меняет статус товара.
Для ролей без доступа к себестоимости колонка и значение полностью исключены.

Изменение статуса: явный выбор, сохранение сервером, защита от двойной отправки,
возврат к подтверждённому значению при ошибке. Конфликт версии требует перечитать
карточку. **ПРЕДЛОЖЕНИЕ:** обязательная причина вывода и возврата, запись старого/
нового статуса и автора. Повторный запрос с тем же результатом не создаёт второе
событие перехода. Право управления ассортиментом требует решения Q02.

### 4.2 Карточка

Карточка постепенно включает: изображение, вес и тип продажи, цену по точкам,
описание и характеристики, состав/ингредиенты, аллергены, технологическую
информацию, сроки/условия хранения, материалы обучения продавцов, историю.
Разделы пустых данных показывают отсутствие сведений, а не выдуманное содержание.
Для каждой группы видно происхождение: iiko или дополнение EOS, дата проверки
и актуальность. Полная ТТК отделена от безопасного состава для продавца.

**ПРЕДЛОЖЕНИЕ:** локальные описания, аллергены, хранение и учебные тексты редактирует
ответственный за продукцию; публикация требует подтверждения профильным человеком
(Q10). Импорт ингредиентов не является доказательством отсутствия аллергенов.
Вес изделия не равен автоматически выходу ТТК или массе единицы склада.
Если API не содержит нужный атрибут, он остаётся неизвестным; локальное уточнение
хранится отдельно с автором и причиной, не маскируется как факт iiko.

### 4.3 Ассортимент и история

Новое изделие попадает в базу только по утверждённому правилу отбора готовой
продукции (Q03). Не вся запись общей номенклатуры iiko — готовое изделие сети.
**ПРЕДЛОЖЕНИЕ:** до подтверждения первичного статуса не разрешать производственный
заказ; назначить один из двух статусов EOS при контролируемой публикации, не
считывать его из меню iiko (Q01). Непроверенная запись остаётся в зоне проверки,
а не получает третий пользовательский статус ассортимента.

`deleted` в iiko — отдельный сигнал качества источника. Он не удаляет изделие и
не переключает D02. **ПРЕДЛОЖЕНИЕ:** при подтверждённой недоступности источника
блокировать новые производственные строки до решения человека, сохраняя статус
EOS и пояснение. Исчезновение из неполной выборки не считается удалением.

Вывод не отменяет автоматически ранее утверждённый план и не переписывает
старые продажи. **ПРЕДЛОЖЕНИЕ:** при новом подтверждении/новой версии заявки
повторно проверять ассортимент; выведенную строку возвращать на решение, а не
молча удалять. Правило уже утверждённых будущих планов закрывается в Q13.
Повторный ввод использует ту же идентичность и историю.

### 4.3a Принятый scope K2 — 09.10.2026

- Полное редактирование: отображаемое название, существующая активная категория
  EOS, описание, характеристики, состав, аллергены, хранение, материалы продавцам.
  Создание нового справочника категорий, фото, цены и редактирование ТТК в K2 не входят.
- Статус сетевой, хранится только в EOS. OFF_SALE остаётся в рабочем каталоге;
  удалённое из EOS изделие скрыто по умолчанию и доступно через отдельный фильтр.
  Оба состояния исключают новые производственные строки. Старые продажи, связи,
  опубликованная партия и уже утверждённые документы сохраняются.
- Восстановление сохраняет статус и все локальные сведения. Повторное добавление
  через тот же UUID восстанавливает ту же запись, статус явно подтверждается.
  Все обычные изменения требуют причины/комментария и expected_version.
- Новое изделие выбирают по названию или UUID в read-only iiko-каталоге, затем
  подтверждают конкретный UUID и статус EOS. Источник должен совпадать с K1;
  неполный/конфликтующий каталог, неизвестная единица или конфликт существующей
  Supply/Sales ID-связи блокируют добавление. Связь по имени не создаётся.
- «Проверено» — отдельное аудируемое действие. Сотрудник/дата задаются сервером;
  правка карточки, статуса, удаление/восстановление снимают отметку. Пустое поле
  не означает отсутствие аллергенов. Прогресс — проверенные / все изделия рабочего
  каталога, включая OFF_SALE, без удалённых и неопубликованных, независимо от поиска.
- Матрица D10 заменяет прежние предложения Q02 о доступе Seller/бухгалтера и
  других ролей. В коде нет отдельного OPERATIONAL_DIRECTOR: существующая роль
  DEPUTY_DIRECTOR соответствует операционному директору / заместителю директора.
  Проверки активного сотрудника и назначенного производства из ActionContext сохраняются.
- Каталог, карточка и история читают EOS DB. Только явные поиск кандидатов и
  подтверждение добавления выполняют read-only запросы iiko; iiko write отсутствует.
  Системные source/UUID/unit/provenance/publication поля не входят в write DTO.

### 4.4 Себестоимость

**ФАКТ из задания:** iikoOffice показывает денежную себестоимость в ТТК;
её получение исследуемыми API не подтверждено. Наличие `getTree`/`getPrepared`
не доказывает денежную себестоимость.

**ПРОВЕРКА Q05/P06:** отдельно исследовать ССС, СПП, ССН, ССНПП, официальные
определения, методы/отчёты, права, даты, склады/подразделения, базовую единицу,
налоги, применимость для изделия и совпадение с iikoOffice. Расшифровки и формулы
заранее не утверждаются. Последняя закупочная цена, средневзвешенная цена Supply
и сумма ингредиентов не могут отображаться как подтверждённая фактическая
себестоимость. Недоступная себестоимость не равна нулю.

При нерешённом Q05 возможна приёмка базы с явным отсутствием себестоимости
только по отдельному решению владельца Q15. Аналитика себестоимости и маржи
до подтверждения метода недоступна. Денежная себестоимость не нужна для
количественного расчёта сырья, но годность ТТК/единиц для него обязательна.

## 5. Часть II — целевой процесс (предложения до gate K)

### 5.1 Последовательность

1. EOS читает согласованные продажи из 3.1V и показывает полноту/давность данных.
2. Рассчитывает объяснимую рекомендацию по изделию, точке и дате; это рекомендация,
   окончательное решение принимает человек. Алгоритм и сезонность пока Q11.
3. Продавец по своей подтверждённой точке вводит/корректирует заявку готовой
   продукции; отклонение от рекомендации сопровождается причиной.
4. Подтверждение фиксирует версию заявки. Черновик после подтверждения не
   изменяет подтверждённую потребность до нового подтверждения. Закрытие окна
   использует последнюю подтверждённую версию; время/дата authoritative в EOS.
5. EOS агрегирует заявки, пригодные остатки и подтверждённые ожидаемые поставки,
   исключает двойное покрытие. Показывает рекомендованный производственный план.
6. Шеф-кондитер проверяет план и предварительный ТТК-расчёт, подтверждает или
   корректирует с причиной. Фиксируются исходный расчёт EOS и решение человека.
7. По утверждённой версии выпуска EOS закрепляет версии ТТК/единиц, пересчитывает
   сырьё и фиксирует подтверждённую потребность цеха. Неизвестные ингредиенты,
   циклы рецептуры и конверсии блокируют передачу.
8. Только подтверждённый дефицит сырья передаётся в canonical Supply; не весь
   валовый расход. Supply решает закупку, распределение и исполнение.
9. Факт выпуска, списания и движения фиксируется из подтверждённого источника;
   EOS сравнивает с утверждённой версией плана и сохраняет причины отклонений.

### 5.2 Ответственность и подтверждения

| Участник | Предлагаемая ответственность |
|---|---|
| `SELLER` | Заявка своей точки, проверка доступных остатков, подтверждение и причина корректировки; без доступа к чужим заявкам/персональным продажам |
| `NETWORK_MANAGER` | Проверка потребности розницы, исправление с причиной; подтверждение вместо продавца требует отдельного правила Q13 |
| `CHEF_CONFECTIONER` | Окончательное содержательное утверждение плана и потребности цеха; объяснение изменений |
| `HEAD_OF_PRODUCTION` | Организация исполнения/контроль факта; замещение шефа только после явного решения Q13 |
| `SUPPLY_MANAGER` | Действия существующего Supply после принятия потребности; не утверждает рецепт вместо шефа |
| `DIRECTOR`, `DEPUTY_DIRECTOR` | Просмотр/контроль в разрешённых scopes; override не подразумевается и требует правила |
| `ADMIN` | Техническая диагностика и разрешённые действия с аудитом; не заменяет бизнес-подтверждение автоматически |

Это проектная матрица новых действий, не изменение текущего RBAC. Пользователь
и сотрудник остаются разными сущностями; контекст ответственности — существующий
ActionContext. Временное исключение Seller SupplyRequest без resolved shift
не переносится на производственные заявки автоматически (Q12).

### 5.3 Версии, остатки, сырьё и план/факт

**ПРЕДЛОЖЕНИЕ:** жизненный цикл плана: черновик → на проверке → утверждён →
в исполнении → закрыт; отклонение/возврат создают события, отмена не удаляет
историю. Точные состояния и API будут утверждены после gate K.

Версия плана хранит ссылки на подтверждённые заявки, датированные остатки,
ожидаемые поставки, покрытие и рекомендацию. Изменение после утверждения —
новая версия с повторной проверкой шефом; старое решение неизменно. Повторная
передача той же версии не создаёт новую закупочную потребность. Если старый
дефицит уже зарезервирован Supply, новая версия требует согласованной дельты,
а не молчаливой замены или повторной закупки (Q14).

Продажи не являются выпуском, списанием, остатком или неудовлетворённым спросом.
Нулевые продажи при неизвестном наличии нельзя считать нулевым спросом.
Формулы количественной потребности, потери, выход, партии, полуфабрикаты,
сроки годности и ограничения мощности уточняются после разведки (Q06/Q11).
Рекомендация о проверке ТТК возможна только по подтверждённым данным;
ТТК никогда не корректируется автоматически.

## 6. Приёмка и остановка

репрезентативные изделия сверены с iikoOffice; компактная таблица и карточка
понятны; неизвестные значения честно обозначены; status round-trip и resync
сохраняют решение EOS; права и история проверены. Полный gate K, допустимые

Текущий результат — документация на review. До её согласования не выполняется
разведка; после согласования разведка требует отдельного задания. Реализация
и deployment также не входят в текущее разрешение.


## K3 — первый локальный проход от 09.10.2026

Историческая запись до повторного read-only доступа; актуальное состояние ниже.

[Отчёт K3](STAGE_3_2_K3_REPORT_2026-10-09.md) фиксирует частичную готовность,
а не завершение ценового слайса. 413 контекстов K1 остаются кандидатами; в текущем
checkout их CSV/manifest/points отсутствуют. Три точки по K1: Матросова 35,
Игарская 25В, Матросова 15. Названия не используются для назначения UUID.

Подтверждённые цены можно импортировать отдельно от публикации/редактирования
продукции. Требуются source, точные UUID продукции/точек, валюта, единица,
полуоткрытый интервал, evidence независимой сверки Office и review hash.
Ноль допустим только как явно подтверждённая сумма. Отсутствие/конфликт не имеют
fallback в defaultSalePrice, чек или выручку. Конфликт отображается «Цена требует
проверки», отсутствие — «Нет подтверждённой цены».

Состояние ассортимента, локальные знания, версия карточки и проверка управляющим
не меняются при импорте цен. Новые карточки автоматически не создаются.
Доступные даты цен означают только подтверждённый период, а не обещание будущей
актуальности; период и время наблюдения видны в карточке.

Read-only iiko reader, подтверждение приоритетов BASE/scheduled/category,
отменённых приказов и единицы/валюты по контрольным изделиям остаются обязательной
незавершённой частью K3. K3/Gate K не закрыты; deployment не выполнялся.


## K3 — продолжение от 09.10.2026: обычные цены готовы к публикации

Актуальные данные получены повторно без зависимости от старых R0/K1 CSV.
363 действующих ordinary prices на три подтверждённые точки, 50 source exclusions
и 10 отсутствующих контекстов. UUID связаны только через текущие mappings;
единицы всех 141 изделий совпали с актуальными catalogue/MeasureUnit.

Владелец подтвердил контрольные значения и RUB/единицы/обычный прейскурант:
«Горячий шоколад» 00667: Матросова 15 — 150/порц, Матросова 35 и Игарская 25В —
120/порц; «Тесто дрожжевое» 01016 — 350/кг; «Заказной Торт Наслаждение» 74615 —
2500/кг на всех трёх точках. Это подтверждение владельца, не самостоятельный
визуальный осмотр iikoOffice агентом.

Read-only collector/regular action обновляют цены только уже published EOS UUID.
Новое изделие автоматически не добавляется. Снимки/аудит/исправления сохраняются;
local knowledge, version, EOS status и manager verification не перезаписываются.
Обычная цена выбирается по точке и `[valid_from,valid_to)`. Категория/размер не
назначаются автоматически. Появление SCHEDULED с ценой, зависящей от времени,
показывает «Цена требует проверки»: дата без времени не задаёт такую цену.
Пересекающиеся расписания нельзя разрешать придуманным приоритетом.

Регулярное обновление локально подготовлено через existing scheduler/outbox,
company interval 60 minutes и explicit approved policy. Production включение
отдельно после review. Срез цены и source observed_at видны в карточке; при сбое
сохраняется последний успешный snapshot с его временем наблюдения, свежесть
не объявляется автоматически подтверждённой. K3 полностью не закрыт из-за
непроверенных SCHEDULED precedence/browser acceptance; Gate K открыт.

## K4 — локальное управление фотографиями EOS, 09.10.2026

Прямое задание владельца утверждает локальную фотографию EOS как приоритетную.
K0–K3 работают на production по текущему подтверждению владельца; прежние записи
о локальном состоянии K3 выше исторические. Это не повторный production audit.

В карточке разрешены загрузка, замена, удаление одного основного фото; фото видно
в таблице, мобильном каталоге и карточке. При отсутствии — «Нет фото», при ошибке
выдачи — «Фото недоступно». Права — D10/K2, включая контекст активного сотрудника
и назначенного производства; других ролей в портал не добавлено.

Фото связано с EOS product UUID, требует причины и expected_version, снимает
«Проверено». Идентичный повтор исходного запроса не увеличивает версию и аудит;
конкурентная иная правка старой версии получает 409. История действий/старые файлы
сохраняются. Название не используется для сопоставления; источник iiko не пишет
local_photo_hash. R0 active photo coverage=0, поэтому downloader/fallback iiko
в K4 не добавлен. При последующем подключении source media оно должно иметь
отдельный указатель, локальная фотография EOS остаётся приоритетной.

K4 реализован локально на review; business/browser/Docker production acceptance
не объявляется выполненной. [Отчёт](STAGE_3_2_K4_REPORT_2026-10-09.md),
[хранение и recovery](STAGE_3_2_K4_STORAGE_RUNBOOK.md). Gate K остаётся открытым.
